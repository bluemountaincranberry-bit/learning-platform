# Project Context

## Что это за проект

Это `Learning App` — приложение для изучения языков через контент.

Базовая идея:
- у нас есть контент: видео, тексты, грамматика, другие учебные источники;
- из контента извлекаются слова и фразы;
- пользователь изучает лексику в контексте;
- система хранит прогресс, learned state и повторения;
- поверх этого можно строить AI-функции, рекомендации, аналитику и интеграции.

Проект одновременно:
- продуктовый;
- учебный;
- инженерный.

То есть цель не только “сделать фичу”, но и строить систему так, чтобы на ней можно было осмысленно практиковать архитектуру, новые технологии и хороший engineering process.

---

## Главная продуктовая идея

Пользователь учит язык не по абстрактным карточкам, а через реальный контент.

Основной сценарий:
1. в систему попадает контент;
2. контент обрабатывается;
3. из него появляются лексемы и учебные элементы;
4. пользователь изучает их;
5. система показывает прогресс, повторения и персональные подсказки;
6. со временем поверх этого растут рекомендации, AI и дополнительные каналы возврата пользователя.

## Что важно про этот проект

Это не просто CRUD-приложение.

Здесь важно тренировать:
- modular thinking;
- event-driven подход там, где он уместен;
- очереди и фоновые процессы;
- DDD/lightweight domain boundaries;
- хороший Laravel backend;
- хороший Vue SPA;
- интеграции и наблюдаемость;
- аккуратное использование AI в продукте.

Новые технологии и техники здесь приветствуются, если:
- они реально помогают архитектуре или обучающей ценности проекта;
- они не добавляют бессмысленную сложность;
- решение остаётся объяснимым и поддерживаемым.

## Принцип модульности

Это modular monolith.

То есть:
- система живёт в одном приложении;
- но внутри неё должны быть понятные бизнес-границы;
- новые фичи не должны бездумно смешивать `Content`, `Learning`, `SRS`, `AI`, `Admin`.

Хороший вопрос перед любым изменением:

`К какому модулю по бизнес-смыслу это относится?`

Не:
- “куда удобнее положить файл”,
- а:
- “кто за это отвечает по смыслу системы”.

---

## Как модули должны взаимодействовать

По умолчанию предпочитаем такую модель:

### 1. Прямой вызов

Используем, когда:
- это простой синхронный use case;
- нет побочного fan-out;
- связь очевидна и локальна.

Пример:
- controller вызывает application service;
- service получает данные из repository;
- service возвращает результат.

### 2. Job / queue

Используем, когда:
- работа тяжёлая;
- её не нужно выполнять в HTTP request;
- есть обработка контента, AI batch, внешние вызовы;
- нужен retry / timeout / background execution.

### 3. Event

Используем, когда:
- “что-то произошло” и на это могут реагировать разные части системы;
- не хочется жёстко связывать модули друг с другом;
- нужна аналитика, уведомления, вторичные действия, Kafka fan-out.

Правило:
- событие описывает факт;
- слушатели реализуют побочные реакции;
- core flow не должен зависеть от случайных вторичных эффектов.

---

## Event-first мышление

Когда это уместно, модули должны общаться через события, а не через скрытые сайд-эффекты.

Типовые события, которые логично иметь в системе:
- content submitted
- content processing requested
- content processing completed
- content processing failed
- lexeme marked learned
- learning session completed
- srs card reviewed
- AI explanation requested
- AI conversation started / message sent

Это не значит, что всё нужно переводить в events.

Это значит:
- важные бизнес-факты лучше выражать явно;
- secondary effects лучше строить вокруг событий;
- Kafka потом можно подключать поверх уже существующих событий.

## Как относиться к Redis, Kafka и async

### Redis

Нормальный базовый выбор для:
- queues;
- cache;
- возможно sessions.

### Kafka

Нужен не как замена приложению, а как event bus для:
- аналитики;
- интеграций;
- независимых consumers;
- обучающего опыта работы с event-driven архитектурой.

### Async mindset

Если операция:
- тяжёлая,
- нестабильная,
- зависит от внешнего сервиса,
- или не нужна пользователю немедленно,

то её надо рассматривать как кандидата на job/event-driven flow.

## Как принимать инженерные решения

При выборе решения приоритет примерно такой:

1. Понятность и объяснимость решения.
2. Соответствие модульным границам.
3. Польза для продукта.
4. Польза для обучающей ценности проекта.
5. Технологическая новизна.

То есть:
- “новое” не должно побеждать “понятное”;
- но если есть два нормальных пути, можно выбрать тот, который учит более сильному подходу.

---

## Что считать хорошим решением в этом проекте

Хорошее решение:
- не ломает модульные границы;
- не тащит лишнюю сложность раньше времени;
- оставляет место для роста;
- тренирует хорошие инженерные привычки;
- помогает потом объяснить, почему система устроена именно так.

Плохое решение:
- сделано “потому что модно”;
- размазывает ответственность;
- смешивает продуктовые и технические слои;
- прячет важные бизнес-факты;
- усложняет код без явной пользы.
