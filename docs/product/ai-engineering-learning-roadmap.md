# Дорожная карта: учу AI-инжиниринг, строя свой мини-LangChain на PHP внутри Blue

## 0. Зачем этот документ

Ты попросил(а) посмотреть на приложение (админку и пользовательскую часть) и
предложить, с чего начать, чтобы одновременно: (а) учиться AI-инжинирингу —
как устроены RAG, agent'ы, tool calling, embeddings, — и (б) сделать что-то
реально полезное для пользователей Blue, а не игрушечный pet-проект в
отдельном репозитории.

Хорошая новость: `docs/architecture/engineering-principles.md` прямо говорит,
что этот проект — учебный инженерный, не только продуктовый. А в
`docs/product/ai-chat-tutor-plan.md` и `docs/product/word-training-module-idea.md`
уже есть продуктовое видение (RAG-репетитор, agent-роли, тренажёр слов). Этот
документ — не замена им, а взгляд с другой стороны: как пройти путь их
реализации так, чтобы по дороге **понять**, как устроен движок, а не просто
подключить SDK.

## 1. Что у тебя уже есть (инвентаризация по факту кода)

Ты уже не с нуля. Ниже — что реально работает сейчас:

### AI-слой (`app/Modules/Ai`)
- **Контракты-абстракции провайдера**: `AiClientInterface` (простой
  completion), `AiJsonClient` (structured output / JSON-режим),
  `AiToolCallingClient` (chat + tool calls), `EmbeddingsClientInterface`.
  Реализации — `OpenAiClient` (REST через `Http::post`, без стриминга) и
  `OllamaClient` (локальная модель) — то есть у тебя уже есть **provider
  abstraction**, один из первых принципов любого AI-фреймворка.
- **Пайплайн анализа контента**: админ создаёт `Content` → `ProcessContentJob`
  токенизирует транскрипт → админ запускает `AiAnalysisRun` →
  `AiContentAnalysisService::analyze()` шлёт транскрипт в `completeJson()` с
  явной JSON-схемой (`responseSchema()`) → получает кандидатов слов/грамматики
  → `CandidateMatchingService` матчит их с каноническим словарём: точное
  совпадение по лемме, а если нет — **свой векторный поиск руками**:
  `embeddings->embed()` + `cosineSimilarity()` по всем эмбеддингам в БД
  (`app/Modules/Ai/Application/CandidateMatchingService.php:127`). Это
  буквально "vector search from scratch" — только линейный, без индекса.
  Порог сходства — `config('ai.analysis.match_threshold')`.
- **Agent, который ты уже написал**: `ContentAgentService`
  (`app/Modules/Ai/Application/Agent/ContentAgentService.php`) — это и есть
  твой первый самодельный "LangChain-аналог". Цикл `for` до
  `MAX_ITERATIONS`, на каждой итерации: спросить модель → если она просит
  вызвать инструмент — вызвать, положить результат обратно в историю → снова
  спросить модель, пока не будет финального ответа. Инструменты — обычные
  классы, реализующие `AgentTool` (`ExtractPdfTextTool`, `CreateContentTool`,
  `RunContentAnalysisTool`, `GetAnalysisCandidatesTool`,
  `SearchExistingLexemesTool`). Жёсткое правило (см.
  `docs/product/ai-chat-tutor-plan.md` и твоё собственное решение из прошлой
  сессии): агент может только предлагать — публикация в живой каталог всегда
  ручной клик админа. Это классический **human-in-the-loop** паттерн.
- **Пользовательский AI пока простой**: `AiExplainLexemeService` — один
  закешированный completion "объясни слово" (кнопка Explain в
  `WordListItem.vue`). `ChatContextAiService` — чат `/chat`
  (`ChatPage.vue` → `AiConversationController`) склеивает историю в один
  текстовый промпт и шлёт `complete()`. **Без RAG** (не подмешивает слова
  пользователя/контент), **без tool calling**, **без стриминга** — модель
  отвечает целиком, фронт ждёт весь ответ.
- **`RecommendationService` — вообще без AI**: рекомендации контента и слов
  — это `inRandomOrder()->limit()` в SQL. Ни эмбеддингов, ни персонализации
  по прогрессу, хотя эмбеддинги для слов в системе уже есть (используются в
  matching выше).

### Инфраструктура вокруг AI, которую можно переиспользовать
- `config/ai.php` + `App\Support\AiConfig` — уже есть флаги `ai.enabled` и
  отдельно `ai.agent.enabled`, лимиты запросов в день на пользователя
  (`ai.rate_limits.explain_per_day`/`chat_per_day`, применяются через
  `App\Http\Middleware\AiRateLimit`). Любая новая пользовательская AI-фича
  (шаги 2-3 ниже) должна идти через этот же middleware и флаги, а не
  придумывать свои.
- Эмбеддинги канонических слов/грамматики уже считаются фоновыми джобами
  (`ComputeCanonicalLexemeEmbeddingsJob`, `ComputeGrammarRuleEmbeddingsJob`, с
  Artisan-командами) — для шага 4 (рекомендации) эмбеддинги, скорее всего,
  уже есть в БД, генерировать их заново не нужно.

### Что не AI, но важно для контекста
- SRS-движок (`srs_cards`/`srs_reviews`, SM-2-подобный) — отдельный,
  неплохо изолированный модуль. Он не AI и не должен им становиться (см.
  `word-training-module-idea.md`, раздел 5: "не переписывать алгоритм
  интервалов").
- Уже есть два продуктовых плана, которые прямо описывают то, что ты хочешь
  строить: `ai-chat-tutor-plan.md` (RAG-репетитор, роли-агенты, memory) и
  `word-training-module-idea.md` (единый тренажёр слов с разными типами
  упражнений).

**Главный вывод**: у тебя уже есть работающий tool-calling agent loop,
provider abstraction, structured output и hand-rolled векторный поиск. Это
буквально ядро того, что делает LangChain — просто оно размазано по
конкретной фиче (админский лёгкий агент) и не оформлено как переиспользуемый
слой. Первая настоящая "AI-инженерная" задача — не писать это с нуля ещё раз,
а **вытащить общий фреймворк из того, что уже работает**, и осознанно пройти
через концепции, которых пока не хватает: RAG, streaming, память, evals.

## 2. Мини-глоссарий (на будущее, когда будешь читать статьи/доки LangChain и т.п.)

- **Prompt engineering** — то, что уже делает `AiContentAnalysisService::buildSystemPrompt()`: явно расписывать формат, ограничения, примеры.
- **Structured output / JSON mode** — просить модель вернуть JSON по схеме, а не свободный текст (`AiJsonClient::completeJson`). Основа для любой автоматизации — без этого нельзя надёжно распарсить ответ.
- **Embeddings** — вектор смысла текста. Используются для *похожести*, а не для генерации (`EmbeddingsClientInterface`, `CandidateMatchingService`).
- **Vector search** — поиск ближайших векторов (сейчас у тебя — линейный перебор + косинусное сходство; в проде это обычно ANN-индекс типа HNSW).
- **RAG (Retrieval-Augmented Generation)** — вместо того чтобы полагаться на память модели, ты сам находишь релевантные факты (retrieval) и подставляешь их в промпт перед генерацией. У тебя пока этого нет нигде на пользовательской стороне — чат отвечает "из головы" модели.
- **Tool calling / function calling** — модель не просто отвечает текстом, а может попросить вызвать конкретную функцию с аргументами (у тебя уже есть — `AiToolCallingClient`).
- **Agent loop** — цикл "спросить модель → выполнить то, что она попросила → снова спросить", пока не будет финального ответа (у тебя уже есть — `ContentAgentService`).
- **Memory** — то, что агент/чат помнит между сообщениями/сессиями: либо сырая история (сейчас так и есть, наивно), либо суммаризация/структурированные факты (`ai-chat-tutor-plan.md` называет это `MemoryAgent`).
- **Streaming** — отдавать токены по мере генерации, а не ждать весь ответ (у тебя нигде не реализовано).
- **Evals** — автоматизированная проверка качества промпта/пайплайна на наборе примеров, аналог unit-тестов, но для качества AI-ответов, а не только "не упало ли".
- **Semantic cache** — кешировать ответ не по точному ключу, а по похожести вопроса (у `AiExplainLexemeService` кеш есть, но по точному `lexeme_id`, не семантический).

## 3. Roadmap: с чего начать (от простого к сложному, каждый пункт — реальная фича)

Порядок ниже специально начинается с пользовательского UI, как ты просил(а),
и постепенно углубляется в "движок". Каждый пункт учит одной-двум концепциям
и опирается на конкретные файлы, которые уже есть.

### Шаг 1 — Стриминг ответа в чате (`/chat`)
**Файлы:** `OpenAiClient::complete`, `AiConversationController::storeMessage`, `ChatPage.vue`.
**Что сделать:** добавить `stream: true` в запрос к OpenAI, читать
Server-Sent Events по мере поступления, отдавать их на фронт через SSE-эндпоинт
(Laravel `StreamedResponse`) вместо одного JSON-ответа; на фронте — читать
`fetch` body как поток и дописывать текст по кусочкам.
**Зачем именно первым:** самый заметный UX-эффект для пользователя (ответ
"печатается" как в ChatGPT) при относительно небольшом объёме кода, и это
фундаментальный механизм, без которого не построить приличный чат-интерфейс.

### Шаг 2 — RAG-репетитор: чат, который знает контент и слова пользователя
**Файлы:** новый `TutorContextService` (уже описан в `ai-chat-tutor-plan.md`,
раздел "Stage 2: Context Builder"), `ChatContextAiService`.
**Что сделать:** прежде чем звать модель, вручную (без библиотек!) собрать
контекст: слова пользователя из `content_lexemes`/`user_lexeme_progress` для
текущего `content_id`, грамматику этого контента, пару примеров предложений —
и подставить это в system prompt. Никаких эмбеддингов здесь пока не нужно —
это "SQL-RAG", самый честный способ понять, что RAG — это *retrieval*, а не
магия, и только потом (шаг 5) заменить часть retrieval на embedding-поиск.
**Зачем:** это ядро паттерна, лежащего в основе почти всех "AI-фич" в
продуктах — генерация, заземлённая на реальных данных, а не на догадках модели.

### Шаг 3 — Персонализированный квиз через structured output
**Файлы:** переиспользовать паттерн `AiJsonClient::completeJson` +
`responseSchema()` из `AiContentAnalysisService`; новый сервис вроде
`QuizGenerationService` в `Modules/Ai/Application`; UI — кнопка "Quiz me" на
`StudyPage.vue`/`ChatPage.vue` (см. `ExerciseGeneratorAgent` в
`ai-chat-tutor-plan.md` и раздел 3.3 `word-training-module-idea.md`).
**Что сделать:** взять слова пользователя в статусе "to learn", попросить
модель сгенерировать 5 заданий (multiple choice/gap-fill) строго по JSON-схеме,
показать их в UI, засчитать в прогресс.
**Зачем:** закрепляет structured output на новом сценарии (не только для
админского пайплайна) и даёт видимую пользе для конечного пользователя.

### Шаг 4 — Осмысленные рекомендации на эмбеддингах
**Файлы:** `RecommendationService`, обобщить `cosineSimilarity()` из
`CandidateMatchingService` в общий helper (например
`Modules/Ai/Application/VectorMath.php`), чтобы не дублировать одну и ту же
математику в третьем месте.
**Что сделать:** заменить `inRandomOrder()` на ранжирование: похожесть на уже
выученные слова (через эмбеддинги, которые уже считаются для канонических
лексем) + сигнал "давно не повторялось" из SRS. Не нужен новый AI-вызов на
каждый рендер — эмбеддинги слов уже есть в БД, это чистая математика поверх
готовых векторов.
**Зачем:** учит, что "AI-движок" — это не всегда LLM-вызов; ранжирование по
векторам — отдельный, дешёвый и быстрый строительный блок.

### Шаг 5 — Свой мини-фреймворк агентов (тот самый "LangChain с нуля на PHP")
**Файлы:** `ContentAgentService`, `AgentTool`, `AgentToolContext`,
`AgentToolDefinition`.
**Что сделать:** вынести из `ContentAgentService` общий, не завязанный на
контент-пайплайн "рантайм" — `AgentRuntime`/`AgentLoop`, который принимает
список `AgentTool`, системный промпт и лимит итераций, и просто крутит цикл
"спросить → выполнить tool → повторить". Дальше на этом рантайме построить
**второго** агента — `StudentTutorAgentService` — с новым набором
инструментов для ученика: `GetMyProgressTool`, `GetDueReviewsTool`,
`SearchMyLexemesTool`, `ExplainGrammarTool`, `GenerateQuizTool`. Строго
read-only/propose-only инструменты — тот же human-in-the-loop принцип, что и
у админского агента, просто здесь "публиковать" почти нечего опасного, но
паттерн стоит сохранить осознанно, а не случайно.
**Зачем:** это и есть ответ на "хочу построить LangChain с нуля, чтобы
понять как это работает" — только не изолированный pet-проект, а
переиспользуемая часть реального приложения, доказавшая себя на одном агенте
и теперь примененная ко второму. Именно на этом шаге виднее всего, что
"фреймворк" — это просто: (1) интерфейс инструмента, (2) цикл, (3) контекст,
(4) лимит итераций/защита от зацикливания.

**Это самый приоритетный шаг** — полный архитектурный разбор с разбивкой на
мини-шаги (5.1-5.11), enterprise-соображениями (безопасность как инвариант
кода, observability, guardrails против prompt injection, мини-ADR по
ключевым решениям) вынесен в отдельный документ:
`docs/architecture/agent-framework-roadmap.md`.

### Шаг 6 — Evals: как понять, что промпт стал лучше, а не просто "по ощущениям"
**Файлы:** новый `tests/Feature/AiContentAnalysisEvalTest.php` (или отдельная
консольная команда `ai:eval`), опирается на `AiContentAnalysisService`.
**Что сделать:** собрать 5-10 эталонных транскриптов с заранее известным
ожидаемым набором слов/грамматики (golden dataset), прогонять анализ и
считать простую метрику (сколько ожидаемых слов найдено, сколько лишнего).
Не про 100% автоматическую оценку качества текста моделью — на старте
достаточно точных/частичных совпадений по ожидаемому набору.
**Зачем:** это стандартная AI-инженерная практика, которой не хватает почти
везде на старте: без evals любое изменение промпта — угадывание. Здесь же
удобно проверять качество квизов из шага 3 и ответов repetitor'а из шага 2.

### Шаг 7 (опционально, когда появится реальная нагрузка) — Семантический кеш
**Файлы:** `AiExplainLexemeService` (уже есть точный кеш по `lexeme_id` —
паттерн для расширения), `ChatContextAiService`.
**Что сделать:** для чата — кешировать ответы не по точному тексту вопроса, а
по похожести эмбеддинга вопроса (если рядом уже был почти такой же вопрос —
не звать модель снова).
**Зачем:** экономия денег/задержки — классическая продакшн-оптимизация AI-
систем, но осмысленна только когда уже есть трафик, поэтому в конце списка.

## 4. Рекомендуемый порядок и почему

1 → 2 → 3 → 4 → 5 → 6 → (7 по необходимости).

Логика: сначала быстрые, видимые пользователю победы в существующем чате
(1, 2, 3) — это держит мотивацию и сразу улучшает продукт. Потом — более
"движковые" вещи (4, 5), где ты уже опираешься на интуицию, наработанную на
первых трёх шагах. Evals (6) — осознанно после того, как появится несколько
настоящих промптов, которые стоит сравнивать между собой, а не раньше. Кеш
(7) — оптимизация, которая имеет смысл только при реальном использовании.

## 5. Что не изобретать заново

- SRS-алгоритм (интервалы, ease factor) — он не AI и не должен им стать
  (`word-training-module-idea.md`, раздел 5).
- Дистракторы для multiple choice в квизах — обычный SQL по `level`/`part_of_speech`, не AI (там же, раздел 4.2).
- TTS/произношение — отдельная фича, не про AI-инжиниринг в смысле LLM/агентов; см. `word-training-module-idea.md`, раздел 4.1, если понадобится позже.
