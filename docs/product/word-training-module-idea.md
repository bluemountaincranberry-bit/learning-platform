# Идея: единый модуль «Тренировка слов»

## 0. Зачем этот документ

Сейчас работа со словами размазана по трём слабо связанным экранам:
`Study` (список to-learn/learned), `Repetitions` (SRS-сессия) и `Check yourself`
(бинарный self-check). У каждого свой поток данных и своя логика, но нет единого
«тренажёра», через который приятно проходить каждый день. Ниже — разбор текущего
состояния, вдохновение из похожих продуктов (Reverso Context, Anki, Duolingo,
Memrise, Quizlet, LingQ) и предложение, как собрать это в один связный модуль,
не ломая модульные границы проекта (`Content` / `Learning` / `SRS` / `AI`).

---

## 1. Что уже есть в приложении

### Данные
- `lexemes` — канонический словарь (слово/фраза, `part_of_speech`, `level`, `status`).
- `lexeme_translations`, `lexeme_examples` — переводы и примеры, с разделением
  «глобальный» / «привязан к конкретному контенту» (`content_id`).
- `lexeme_associations` — связь `lexeme_id → related_lexeme_id` с полем `type`
  (`synonym`/`antonym`/`related`/`collocation`, свободная строка, ничем не
  ограничена на уровне БД). **Уже используется для синонимов** (см. ниже) —
  и то же самое поле `type='collocation'` можно занести без каких-либо
  миграций, схема это уже поддерживает.
- `content_lexemes` + `content_lexeme_links` — вхождения слова в конкретный контент,
  привязка occurrence → canonical lexeme (см. `docs/product/epic/global-lexeme-catalog-epic.md`).
- `user_lexeme_progress` — факт «слово выучено» (`learned_at`), пока привязан к
  `content_lexeme_id`, эпик уже описывает переход на `lexeme_id`.
- `srs_cards` / `srs_reviews` — SM-2-подобный планировщик (`ease_factor`,
  `interval_days`, `next_review_at`), карточка идентифицируется строкой `item_key`
  (`type:text`), а не `lexeme_id` — это отдельная нестыковка с канонической моделью.

### Обновление (после текущей итерации, см. git log) — уже сделано
- **Admin**: полноценный Filament-ресурс `App\Filament\Resources\Lexemes\LexemeResource`
  — CRUD канонической лексемы + 3 relation manager'а: `Examples`, `Translations`,
  `Associations`. Через `Associations` админ уже может проставить `type=synonym`,
  `antonym`, `related` или **`collocation`** — форма это не ограничивает, просто
  сейчас никто ещё не заполнял `collocation`-записи вручную/через AI.
- **API + SPA**: `GET /api/content/{id}/lexemes` и `GET /api/me/learned-lexemes`
  теперь возвращают `associations: {lemma, type}[]` (все типы, не только synonym)
  и `examples: {example, translation, is_primary}[]` (до 3 штук, content-scoped
  первыми). `StudyPage.vue`/`MyWordsPage.vue` уже рендерят `type==='synonym'`
  бейджами и раскрывающийся список примеров — **но только в списочном
  представлении**, не в виде отдельной карточки слова. Это ровно тот кусок,
  который должен переехать в `WordCard` (см. 3.2) — переиспользовать сами
  API-поля не нужно, они уже в нужной форме.

**Что именно перенести в UI из этой итерации, когда будет строиться `WordCard`:**
- ✅ Есть в API, есть в списочном UI, нужно только скопировать в `WordCard`:
  перевод, до 3 примеров с раскрытием, синонимы-бейджи.
- ⚠️ Есть в API, нет нигде в UI: `associations` с `type` отличным от
  `synonym` — сейчас `antonym`/`related`/`collocation` приходят с бэкенда, но
  фронт их просто игнорирует (фильтр `=== 'synonym'` жёстко зашит). Для
  коллокаций это и есть недостающий кусок — см. 4.1.5.
- ❌ Нет ни в API, ни в UI: то, чего не было и до этой итерации — аудио,
  явный статус слова по стадиям, типы упражнений (3.3), игровой слой (3.6).

### Экраны и логика
- **StudyPage** (`resources/js/spa/pages/StudyPage.vue`) — список слов контента:
  to-learn / learned, кнопки «Explain» (AI), «Add to reviews», «Mark learned».
  Список, не тренажёр — нет карточки, нет фокуса на одном слове.
- **RepetitionsPage** — берёт due-карточки из SRS, показывает слово текстом,
  пользователь сам жмёт Again/Good/Easy. Нет перевода, произношения, примера —
  чистое self-grading без опоры.
- **CheckYourselfPage** (`SelfCheckService.php`) — по контенту берёт до 10 уже
  выученных слов, вопрос «Know / Don't know», в конце — процент. Очень простой,
  не запоминает по каким словам был провал (не заводит в SRS автоматически).
- **MyWordsPage** — таблица выученных слов с фильтрами, без тренировочного режима.

### Чего категорически нет
- Аудио/произношения/TTS — нет ни одного упоминания в коде (`grep` по
  audio/pronunciation/tts/speech — пусто).
- Единой карточки «одно слово на экран» с изображением/примером/произношением.
- Разных типов упражнений (multiple choice, набор перевода, listening, gap-fill) —
  везде либо «know/don't know», либо ручная оценка 1/3/5.
- Явного статуса слова по стадиям (`new → learning → review → mastered`) —
  есть только бинарное `learned_at` + отдельно параллельный SRS-статус по ключу.
- Игровых механик (streak, дневная цель, очки, уровни).

**Вывод**: технический фундамент (канонический словарь, переводы, примеры, SRS-
движок) уже приличный. Не хватает продуктового слоя — самого «тренажёра» с
понятными режимами и хорошей карточкой слова.

## 2. Что подсмотреть у других продуктов

| Продукт | Что берём |
|---|---|
| **Reverso Context** | Слово всегда показывается **в контексте** — реальные примеры предложений с переводом с двух языков параллельно. Это сильно бьётся с тем, что у нас уже есть `content_lexemes`/`lexeme_examples` — контент-контекст должен быть на первом экране, а не только в admin. Плюс отдельный блок «похожие поисковые фразы» (`warm bathrobe`, `wearing a bathrobe`, `bathrobe and slippers`) — это и есть коллокации, у нас для них уже есть `lexeme_associations.type='collocation'`, не хватает только (а) кто-то их заполнит и (б) показа в карточке. |
| **Anki / SRS-классика** | Чёткое разделение «Show answer» → потом оценка (Again/Hard/Good/Easy), но с явным раскрытием ответа между вопросом и оценкой — у нас в Repetitions оценка доступна сразу, без «сначала вспомни → потом посмотри». |
| **Duolingo** | Игровой каркас поверх упражнений: streak, дневная цель, XP, разные типы заданий вперемешку в одной сессии (выбор перевода, набор слова, аудирование), лёгкий/жёсткий режим на ошибку («Again» слово скоро возвращается в ту же сессию). |
| **Memrise** | Обучение через «стадии»: new → learning → review, разная механика на каждой стадии (сначала просто показать и дать «запомнить», потом — активная проверка). Использует видео/аудио носителей языка. |
| **Quizlet** | Гибкость режимов над одним и тем же набором карточек: Flashcards (просто листать), Learn (адаптивно, с multiple choice + write), Test (билет с разными типами вопросов), Match (игра на скорость). Один датасет — много форматов тренировки. |
| **LingQ** | Статус слова по цветам (новое / знакомое 1-4 / известное), явно продвигается кликом пользователя по слову в тексте — статус слова это первичный объект, а не побочный продукт «learned/not learned». |

Общий паттерн, который стоит перенять: **один и тот же словарный набор** прогоняется
через **разные режимы тренировки**, а не через разные, не связанные друг с другом
страницы с разными моделями данных.

## 3. Предлагаемая концепция

### 3.1 Модель статуса слова (расширить `user_lexeme_progress`)

Вместо бинарного `learned_at`, ввести явный жизненный цикл на **каноническом**
`lexeme_id` (в русле уже запланированного эпика global-lexeme-catalog):

```
new → learning → review → mastered
              ↘ (провал на review) ↗
```

- `new` — слово встретилось в контенте, пользователь ещё не начал его учить.
- `learning` — пользователь начал изучать (в первый раз увидел карточку в
  режиме «Изучение»), но SRS-интервал ещё короткий (< 1 дня / первые повторения).
- `review` — прошло 1+ успешных повторений, карточка ушла в SRS с растущим
  интервалом.
- `mastered` — интервал вырос выше порога (например 60+ дней) и/или N успешных
  повторений подряд.

Это по сути состояние, которое уже почти существует (`SrsCard.state`:
`reviewing`/`relearning`) — стоит унифицировать с `user_lexeme_progress`, чтобы
UI показывал один согласованный статус, а не два независимых.

### 3.2 Единый экран карточки слова, разный «фасад» под режим

Общий компонент `WordCard`, но с двумя явно разными представлениями:

**A. Learn-facing (режим изучения нового / повторного знакомства)**
Цель — дать максимум опоры, ничего не тестировать.
- Слово крупно + часть речи + уровень (A1..C2).
- 🔊 произношение (TTS/audio) — см. раздел 4.1.
- Перевод сразу виден.
- 1-2 примера предложения с переводом (Reverso-style), приоритет — пример из
  того контента, откуда слово пришло (`lexeme_examples.content_id`). **Готово**:
  API уже отдаёт до 3 штук в нужном порядке, просто перенести рендер из
  `StudyPage.vue` в `WordCard`.
- Синонимы бейджами (`type='synonym'`) — **готово** на уровне API, рендер уже
  есть в `StudyPage.vue`/`MyWordsPage.vue`, перенести в `WordCard` тем же кодом.
- Коллокации бейджами (`type='collocation'`) — той же строкой `associations`
  из API, просто ещё не отфильтровано по этому типу во фронте (сейчас фильтр
  `type === 'synonym'` захардкожен) и почти наверняка пусто в БД, пока никто
  не добавил `collocation`-записи через admin `AssociationsRelationManager`.
- Кнопки: «Уже знаю» (сразу → `review`/`mastered`, пропустить обучение) /
  «Учить» (следующая карточка, слово уходит в `learning`).
- Никакой оценки правильности — здесь нечего проверять.

**B. Test-facing (режим повторения / проверки)**
Цель — заставить вспомнить, потом показать ответ.
- Сначала **только слово** (или только перевод — зависит от направления,
  см. 3.4), без перевода и примера.
- Пользователь сам вспоминает → жмёт «Показать ответ».
- После раскрытия — перевод + пример + произношение, и только теперь оценка:
  «Не помню» / «Помню, но с трудом» / «Легко» (мапится на грейды SRS 1/3/5).
- Опционально — активные форматы вместо чистого recall (см. 3.3), которые сами
  дают объективный сигнал правильности вместо самооценки.

Это чинит главную проблему текущего `RepetitionsPage`: там нет разделения
«вспомни → потом смотри», плюс совсем нет опоры (перевод/пример/аудио) — только
голое слово и сразу оценка.

### 3.3 Типы упражнений в test-режиме (крутить вперемешку, как в Quizlet Learn)

- **Recall + self-grade** — как сейчас, но с раскрытием ответа (дефолт, самый
  дешёвый в реализации).
- **Multiple choice** — слово → выбрать перевод из 4 вариантов. Дистракторы
  берём из слов того же `level`/`part_of_speech` пользователя (не нужен AI,
  чистый SQL по `lexemes`).
- **Type the translation** — набрать перевод текстом, сверка с нормализацией
  (без учёта регистра/пунктуации).
- **Listening** — проиграть аудио, пользователь выбирает/печатает слово
  (требует TTS).
- **Gap-fill из примера** — предложение из `lexeme_examples` с пропущенным
  словом (уже есть данные, ничего нового генерировать не надо).

Формат выбирается по стадии слова: `learning`/ранний `review` — больше опорных
форматов (multiple choice, gap-fill); зрелый `review` — больше чистого recall.
Это соответствует Memrise-подходу «разная механика на разной стадии».

### 3.4 Направление тренировки

Дать пользователю выбор (или чередовать автоматически):
- **Target → Native** (слово на изучаемом языке → перевод) — узнавание, легче.
- **Native → Target** (перевод → слово) — продукция, сложнее, тренирует
  активный словарь.

### 3.5 Композиция сессии («игра» из вопроса)

Единая точка входа "Тренировка" вместо трёх разных страниц:
1. Пользователь жмёт «Тренировать слова» (общая кнопка, не по трём отдельным
   пунктам меню).
2. Сессия собирается из очереди:
   - все `due` SRS-карточки (просрочены/подошёл срок) — приоритет №1;
   - N новых слов (`new`, лимит в настройках, дефолт 5-10/день — daily goal,
     как в Duolingo);
   - немного слов в статусе `learning`, которые проваливались недавно —
     «reinforce».
3. Внутри сессии learn-карточки и test-карточки визуально различаются (бейдж
   режима), но идут одним потоком, а не отдельными вкладками.
4. Проваленное слово (`Again`) возвращается **в ту же сессию** ещё раз ближе
   к концу, а не только откладывается в SRS на завтра — так делает Duolingo и
   это ощутимо снижает «забыл через 2 минуты».
5. В конце — экран итога: сколько новых выучено, сколько повторено, streak,
   прогресс дневной цели.

### 3.6 Лёгкий игровой слой (не переусложнять)

- Дневная цель (например, 10 карточек) + прогресс-бар в шапке приложения.
- Streak (дней подряд с выполненной целью) — считается по факту сессии,
  не нужен отдельный сложный движок.
- Ничего сложнее (лиги, соревнования) не добавлять на первом этапе — это не
  то, ради чего строится проект (см. `PROJECT_CONTEXT.md`: не тащить лишнюю
  сложность раньше времени).

## 4. Что нужно добавить технически

### 4.1 Произношение / аудио
Сейчас нет вообще. Варианты по возрастанию сложности:
1. **Web Speech API (`SpeechSynthesis`) на клиенте** — бесплатно, без бэкенда,
   качество разное по браузерам/языкам, но закрывает MVP за один спринт.
2. **TTS-провайдер на бэкенде** (например через существующий `AI`-модуль,
   который уже умеет ходить к внешним AI-клиентам) — сгенерировать и закэшировать
   mp3 на слово/язык, отдавать по URL. Дороже, но качественнее и стабильнее.
3. Комбинация: Web Speech API как fallback, серверный TTS — как основной путь
   с кэшем (аналогично тому, как уже кэшируется AI-объяснение в
   `AiExplainLexemeService` — `Cache::put` на `ai:explain:{id}:{lang}`, тот же
   паттерн подходит и для аудио-URL).

### 4.1.5 Коллокации — что реально нужно сделать

Это **не** новая схема БД и не новый бэкенд-эндпоинт — `lexeme_associations`
и API (`associations: {lemma, type}[]`) уже несут `type='collocation'`
наравне с `synonym`/`antonym`/`related`. Остаётся два отдельных, независимых
куска работы:

1. **Наполнение данными** — либо вручную через admin
   `App\Filament\Resources\Lexemes\RelationManagers\AssociationsRelationManager`
   (форма уже принимает `type=collocation`), либо через AI-кандидатов: тип
   `collocation` уже объявлен в `content_lexeme_candidates.type`
   (`2026_07_22_120001_create_content_lexeme_candidates_table.php`), не хватает
   только шага "принять кандидата-коллокацию → записать её как
   `LexemeAssociation`" в `AiCandidateApplyService` (сейчас он пишет только в
   `lexemes`/`lexeme_examples`/`lexeme_translations`, коллокации туда не льёт).
2. **Рендер в `WordCard`** — обобщить фильтр `type === 'synonym'`, который уже
   есть в `StudyPage.vue`/`MyWordsPage.vue` (функция `synonymsOf`), в что-то
   вроде `associationsByType(lexeme, 'collocation')`, и вывести отдельным
   блоком под примерами (см. 3.2).

### 4.2 Дистракторы для multiple choice
Не нужен AI — обычный запрос: другие `lexemes` того же `language`+`level`+
(желательно) `part_of_speech`, у которых у пользователя нет прогресса или он
уже `mastered` (чтобы не путать с тем, что реально учится).

### 4.3 Единый статус слова
- Свести `UserLexemeProgress` к каноническому `lexeme_id` (см. эпик
  `global-lexeme-catalog-epic.md`, он уже это планирует).
- Добавить `state` (`new/learning/review/mastered`) на `user_lexeme_progress`
  или вычислять его из связанной `SrsCard` (join по `lexeme_id` вместо текущего
  хрупкого join по `item_key`/`type:text` строке в `SrsService::getDueCards`).
- Перевести `SrsCard.item_key` на `lexeme_id` заодно — уберёт текущий SQL-хак
  с конкатенацией строк для сопоставления.

### 4.4 API уровня "session" (Learning-модуль)
Новый сервис в `Modules/Learning/Application`, например `TrainingSessionService`:
- `buildSession(User $user, array $options): array` — собирает очередь
  (due + new + reinforce) по правилам 3.5.
- `recordAnswer(...)` — маршрутизирует ответ либо в `UserLexemeProgress`
  (learn-режим: «уже знаю»/«учить»), либо в существующий `SrsService::reviewCard`
  (test-режим: грейд).

Это остаётся внутри `Learning`, использует `SRS` через существующий контракт
`SrsServiceInterface`, не лезет в `Content`/`AI` напрямую — соответствует
модульным границам, описанным в `PROJECT_CONTEXT.md`.

## 5. Как это соотносится с модулями проекта

- **Content** — не меняется в логике, только становится источником примеров/
  переводов/уровня для карточки (уже есть).
- **Learning** — получает новый «оркестрирующий» сервис сессии тренировки;
  сюда же логично переехать текущий `SelfCheckService` как один из режимов
  test-facing карточки, а не отдельная фича.
- **SRS** — не переписывать алгоритм интервалов (это осознанно out of scope и
  в эпике каталога), но: (a) избавиться от `item_key`-строки в пользу
  `lexeme_id`, (b) `reviewCard` как было, вызывается из новой сессии.
- **AI** — используется только там, где реально даёт ценность: TTS (если
  выбран серверный вариант) и, отдельно уже существующий, "Explain" остаётся
  доступной кнопкой на карточке в learn-режиме. Генерация дистракторов — не
  AI, обычный SQL (см. 4.2), не стоит тащить AI туда, где не нужно.

## 6. Поэтапный план

**MVP (1 модуль вместо 3 страниц)**
1. Компонент `WordCard` с двумя фасадами (learn/test).
2. Web Speech API для произношения (без бэкенда).
3. `TrainingSessionService`: очередь due + new, без reinforce-логики.
4. Recall + self-grade как единственный test-формат (расширение текущего
   Repetitions, но с раскрытием ответа перед оценкой).
5. Единая точка входа «Тренировать» в навигации вместо Study/Repetitions/
   Check yourself по отдельности (те страницы можно оставить как admin/debug
   views или убрать после переноса функциональности).

**V2**
1. Multiple choice + type-the-translation форматы.
2. Явный `state` (`new/learning/review/mastered`), синхронизированный с SRS.
3. Провал → возврат карточки в конец текущей сессии.
4. Дневная цель + streak.

**V3**
1. Серверный TTS с кэшем аудио по аналогии с кэшем AI-объяснений.
2. Listening-упражнения.
3. Gap-fill из примеров предложений.
4. Направление тренировки (target→native / native→target), настраиваемое
   пользователем.

## 7. Открытые вопросы для обсуждения

- Объединять ли `Study`/`Repetitions`/`Check yourself` в одну страницу сразу,
  или оставить старые как есть и добавить новую «Тренировку» параллельно на
  первое время (safer migration, меньше риска сломать текущий поток)?
- Серверный TTS — через какого провайдера (важно, чтобы вписывался в уже
  существующий `AiClientInterface` контракт) и нужен ли он вообще в MVP, или
  Web Speech API достаточно надолго?
- Нужен ли отдельный экран настроек тренировки (дневная цель, направление,
  включить/выключить типы упражнений) уже в MVP, или сделать это позже с
  разумными дефолтами?
