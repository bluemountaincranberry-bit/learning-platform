# ADR-001: Один координатор на домен, а не рой независимых агентов

## Статус
Принято.

## Контекст

При проектировании multi-agent системы для Blue был соблазн сразу построить
набор специализированных агентов, общающихся друг с другом:
`TutorAgent → MemoryAgent → ExerciseAgent → GrammarAgent → ReviewAgent →
VocabularyAgent`. Так часто выглядят демонстрационные multi-agent системы
в статьях/докладах.

## Решение

Не создавать заранее набор равноправных, самостоятельно общающихся друг с
другом агентов. Вместо этого — **один координатор на домен** (`TutorAgent`
для ученика, `ContentAgentService` для админа — уже существует), который
сам решает, вызвать ли простой `Tool`, передать управление специализированному
`Agent` через handoff (ADR-006), или запустить детерминированный `GraphRunner`
(см. `ai-platform-vision.md`, раздел 7). Специализированные агенты
(`ExerciseAgent`, `ReviewAgent` и т.д.) существуют, но не общаются друг с
другом напрямую — только через координатора.

Третий координатор-корень заводится только когда появляется домен с
реально другой аудиторией/профилем риска (например, отдельный B2B-контур) —
не заранее "про запас".

## Почему

- **Коммуникация.** Рой агентов, общающихся друг с другом, требует протокола
  координации (кто кого может вызвать, в каком порядке, как разрешать
  конфликты) — это сложность, которая ничего не даёт при двух-трёх агентах.
- **Стоимость и предсказуемость.** Каждый переход между агентами — минимум
  один дополнительный LLM-вызов. Без единой точки принятия решения число
  вызовов на один запрос пользователя растёт неконтролируемо.
- **Отладка.** Один координатор с явным логом решений ("вызвал tool X",
  "передал управление агенту Y") — трассируется линейно. Рой агентов без
  координатора — граф вызовов, который сложно восстановить постфактум даже
  с трейсингом.
- **Безопасность.** Правило "агент не публикует в живой каталог без
  подтверждения человека" (см. `agent_human_in_the_loop_apply` в памяти
  проекта) проще держать инвариантом, когда точек входа в систему две
  (координатора), а не десять.

## Альтернативы, которые рассматривались и отклонены

- **Полный рой агентов с прямой коммуникацией друг с другом** — отклонено:
  никакой текущей задачи Blue не требует такой гибкости, а сложность
  реальна с первого дня.
- **Единственный агент на всё приложение** (и админ, и ученик) — отклонено:
  разная аудитория и разный профиль риска (админ работает с черновиками
  контента, ученик — с персональными данными обучения) оправдывают
  разделение на уровне координатора, а не только на уровне промпта.

## Последствия

- Положительные: предсказуемая стоимость, линейная трассируемость, простая
  модель безопасности.
- Отрицательные: координатор может стать узким местом/большим классом при
  росте числа сценариев — если это произойдёт, следующий шаг — не "больше
  агентов", а декомпозиция самого координатора на явные `GraphNode` (см.
  `agent-framework-roadmap.md`), а не превращение его в ещё один
  специализированный агент в рое.
