# ADR-002: Tools для простых задач, Agent — только когда нужен собственный reasoning loop

## Статус
Принято.

## Контекст

Почти любую возможность системы можно реализовать либо как `Tool` (одна
функция, один вызов модели вокруг неё), либо как полноценный `Agent`
(собственный `AgentLoop`, возможно — свои под-инструменты, несколько
LLM-вызовов подряд). Соблазн — заводить агента на каждую функциональную
область ("GrammarAgent", "VocabularyAgent", "ProgressAgent" и т.д.), даже
там, где хватило бы одной функции.

## Решение

По умолчанию — `Tool`. `Agent` заводится только когда задачу нельзя закрыть
одним completion-вызовом с уже собранными входными данными — то есть когда
нужен собственный цикл "получить данные → решить, что дальше → возможно
скорректировать → проверить результат".

Явная граница на примере (см. `ai-platform-vision.md`, раздел 4):
- **Tool**: "Объясни, что такое Present Perfect" — вопрос известен, ответ —
  один вызов с готовым контекстом. `ExplainGrammarTool`.
- **Agent**: "Разбери мою ошибку в этом предложении" — нужно: найти
  релевантное правило → сопоставить с тем, что написал пользователь →
  сформулировать объяснение именно для этого случая → проверить, что
  объяснение соответствует уровню ученика. `GrammarAgent`.

Все инструменты реализуют один и тот же интерфейс `AgentTool`
(`definition()` + `execute()`, включая `sideEffect`, ADR не переопределяет
эту механику — она уже описана в `agent-framework-roadmap.md`, шаг 5.3).

## Почему

- **Стоимость.** Один `Tool`-вызов — предсказуемый 1 LLM-запрос. Полноценный
  `Agent` — переменное число запросов (до `MAX_ITERATIONS`). Заводить агента
  там, где хватает функции, — платить за реasoning, который не нужен.
- **Тестируемость.** `Tool` тестируется как обычная функция/сервис. `Agent`
  требует сценарных тестов с фейковым `AiToolCallingClient` (шаг 5.10) —
  дороже в поддержке, оправдано только реальной сложностью задачи.
- **Прямой доступ модели к БД исключён в обоих случаях**: `LLM → Tool →
  Service → Database`, никогда `LLM → Database` напрямую — модель не должна
  формировать SQL и не должна видеть сырую схему.

## Альтернативы, которые рассматривались и отклонены

- **Агент на каждую функциональную область** — отклонено: большинство
  перечисленных в черновиках возможностей (объяснение известной грамматики,
  поиск по словарю, получение прогресса) — однократные LLM-вызовы с готовым
  контекстом, не требуют собственного reasoning loop.
- **Один универсальный "SuperTool" с большим количеством параметров вместо
  много маленьких Tools** — отклонено: маленькие, узкие Tools проще
  описать модели, проще проверить (`sideEffect` на каждый), проще
  протестировать по отдельности.

## Последствия

- Положительные: предсказуемая стоимость по умолчанию, простая
  тестируемость большинства возможностей.
- Отрицательные: граница Tool/Agent требует суждения при добавлении новой
  возможности — не автоматическое правило. Если на практике граница часто
  спорна для конкретной фичи — сигнал, что стоит явно проверить на реальном
  сценарии (написать оба варианта, сравнить), а не решать умозрительно.
