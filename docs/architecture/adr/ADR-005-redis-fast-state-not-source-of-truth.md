# ADR-005: Redis — быстрая проекция/short-term память, не источник истины для durable state

## Статус
Принято.

## Контекст

Redis уже используется в Blue как backend очереди (`QUEUE_CONNECTION=redis`,
Horizon) и поднят в `docker-compose.yml`. При проектировании памяти
AI-агентов и состояния workflow возникает вопрос: что именно хранить в
Redis, а что — в Postgres. Черновики архитектуры предлагали и то, и другое
для разных вещей (`agent_run:12345` статус хода; short-term память диалога)
без явного разграничения принципа выбора.

## Решение

Redis используется для двух вещей, обе — по природе эфемерные:

1. **Быстрая проекция статуса выполнения** (`agent_run:{id}` — "выполняется
   ли сейчас этот ход", для live-опроса UI и дедупликации параллельных
   запусков). Не источник истины.
2. **Short-term память диалога** (`conversation_id`, последние сообщения,
   рабочий контекст текущего хода) — приемлемо эфемерно: потеря при
   рестарте некритична, пользователь может переспросить.

Postgres остаётся источником истины для всего, что обязано пережить
рестарт/эвакуацию кэша:

- **Long-term память ученика** (`user_lexeme_progress`, `srs_cards`, будущие
  `learner_memory_profiles`) — уже так устроено сегодня.
- **Durable state приостановленных workflow** (`agent_graph_runs`) — пауза
  может длиться часы/дни (`HumanCheckpointNode`, `ai-platform-vision.md`
  раздел 7), Redis не годится как единственное хранилище для этого.

## Почему

- **Критерий выбора — не "что быстрее", а "что можно позволить себе
  потерять".** Если потеря данных при сбое Redis означает "пользователь
  перепишет сообщение" — Redis подходит. Если потеря означает "недельный
  процесс подготовки урока пропал, и админ не может понять, на чём он
  остановился" — это обязано быть в Postgres.
- **Redis как кэш, не как БД.** Уже существующий паттерн в проекте
  (`AiExplainLexemeService` кэширует объяснения через `Cache::put` с TTL,
  сейчас на `database`-драйвере — планируется перевод на Redis) — та же
  логика: Redis ускоряет, не заменяет собой запись истины.
- **Семантическая память — не в Redis.** Наблюдения об ученике
  ("постоянно путает Present Perfect") нужно искать по смыслу, не по ключу
  — это задача Elasticsearch (`ai-platform-vision.md`, раздел 9.1), не
  Redis, при том что оба технически могли бы хранить текст.

## Альтернативы, которые рассматривались и отклонены

- **Redis как единственный источник состояния workflow** (без Postgres) —
  отклонено: недопустимо для процессов, которые могут стоять на паузе
  днями; риск тихой потери состояния при эвакуации/рестарте Redis.
- **Postgres для всего, включая short-term контекст диалога** — отклонено:
  избыточная нагрузка на БД под то, что по природе эфемерно и не требует
  durability; Redis уже в стеке и ничего не стоит использовать здесь.

## Последствия

- Положительные: явный, проверяемый критерий "Redis vs Postgres" для любой
  новой фичи, не нужно решать заново каждый раз.
- Отрицательные: два места хранения состояния для, по сути, одного и того
  же "хода агента" (быстрый статус в Redis + durable state в Postgres)
  требуют аккуратной синхронизации — Redis-проекция обновляется из того же
  кода, что пишет в Postgres, не независимо.
