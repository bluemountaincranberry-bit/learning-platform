# ADR-003: Kafka — только event backbone, не транспорт для agent-to-agent

## Статус
Принято.

## Контекст

В Blue уже есть скелет Kafka-интеграции: `PublishContentSubmittedToKafka`
(листенер, публикует `content.lifecycle`-события), `ConsumeKafkaCommand`
(консьюмер) и `NullKafkaProducer` как текущая no-op реализация продюсера
(реальный — по заметке `KAFKA-02` в `AppServiceProvider.php`). При
проектировании multi-agent системы возникает соблазн использовать этот же
Kafka и для связи между агентами — например, `TutorAgent` публикует
"запроси упражнение", `ExerciseAgent` подписан и отвечает через другой топик.

## Решение

Kafka используется **только** как event backbone — асинхронная шина фактов
о том, что произошло (`exercise.completed`, `content.lifecycle`), с
несколькими независимыми консьюмерами (консолидация памяти, аналитика,
recommendation engine, уведомления). Kafka **не** используется как
транспорт для agent-to-agent коммуникации — handoff между агентами всегда
прямой и синхронный (см. ADR-006): `TutorAgent` вызывает `AgentLoop`
целевого агента напрямую, в рамках того же job'а, и ждёт результат.

```
Правильно:  TutorAgent → (прямой вызов AgentLoop) → ExerciseAgent
Неправильно: TutorAgent → Kafka → ExerciseAgent
```

## Почему

- **Agent handoff — это запрос-ответ с ожиданием результата** (координатору
  нужен ответ агента, чтобы продолжить свой ход). Kafka — pub/sub без
  гарантии немедленного ответа; городить синхронный RPC поверх
  асинхронной шины — известный анти-паттерн (request-reply через
  message broker), который добавляет сложность (корреляция запрос/ответ,
  таймауты, ретраи) без выгоды по сравнению с прямым вызовом.
- **Гонки и потерянные сообщения.** Синхронная логика между агентами
  (например, guardrail на глубину handoff, ADR-006) становится сложно
  проверяемой, если коммуникация асинхронна и её порядок не гарантирован.
- **Отладка.** Прямой вызов трассируется линейно (span → дочерний span,
  раздел 10 `ai-platform-vision.md`). Коммуникация через шину сообщений
  требует сшивать трейсы через correlation id между продюсером и
  консьюмером — лишняя сложность там, где связь и так внутрипроцессная.
- **Экономия инфраструктуры.** Kafka-скелет уже есть в проекте — включение
  его под события AI-системы (`exercise.completed` и т.п.) не требует
  новой интеграции, только новых топиков и консьюмеров.

## Альтернативы, которые рассматривались и отклонены

- **Kafka как универсальная шина для всего, включая handoff** — отклонено
  по причинам выше.
- **Отдельная синхронная message-очередь (RabbitMQ RPC-паттерн) для
  handoff** — отклонено: прямой вызов `AgentLoop` в рамках одного job'а
  проще и не требует новой инфраструктуры вообще.

## Последствия

- Положительные: чёткое разделение "что произошло" (Kafka, асинхронно) от
  "что делать прямо сейчас" (handoff, синхронно) — меньше вариантов
  архитектурной путаницы.
- Отрицательные: если в будущем понадобится agent-to-agent коммуникация
  между независимыми деплойментами (не в рамках одного Laravel-приложения)
  — этот ADR придётся пересматривать явно, а не расширять Kafka под это
  задним числом.
