# ADR-004: Свой GraphRunner на PHP, а не обвязка вокруг LangGraph

## Статус
Принято.

## Контекст

Для многошаговых, частично детерминированных процессов (Workflow Engine,
`ai-platform-vision.md` раздел 7) нужен движок оркестрации: узлы, рёбра,
условные переходы, паузы на человеке, fan-out/fan-in. LangGraph — известная,
проверенная реализация этой идеи, но написана на Python.

## Решение

Строить свой минимальный движок (`GraphNode`/`GraphState`/`GraphRunner`,
детально — `agent-framework-roadmap.md`, разделы 7, 12, 13) на PHP поверх
уже существующих примитивов Laravel (`Bus::batch()` для fan-out/fan-in,
`Http::pool()` для конкурентного I/O, Eloquent для состояния), а не
подключать LangGraph как отдельный Python-сервис за HTTP.

## Почему

- **Явная учебная цель проекта.** Blue — не только продуктовый, но и учебный
  инженерный проект (`docs/architecture/engineering-principles.md`); прямой
  запрос — понять, как устроена оркестрация, строя её самому, а не вызывая
  чужую реализацию через сеть.
- **Фрагментация стека.** LangGraph как отдельный Python-микросервис — это
  второй язык, второй деплоймент, отдельный мониторинг, отдельная команда
  для его эксплуатации (или тот же человек, но контекст-свитчинг между
  экосистемами) — ощутимая операционная цена для двух-трёх агентов.
- **Сетевой прыжок на каждый шаг графа.** Вызов внешнего сервиса на каждый
  `GraphNode` добавляет задержку и точку отказа, которых нет при вызове
  метода в том же процессе/очереди.
- **Достаточность для реального масштаба.** Нужный набор примитивов —
  последовательность, условное ветвление, пауза на человеке, fan-out/fan-in,
  вызов агента как узла (`ai-platform-vision.md`, раздел 7) — не требует
  полноты LangGraph (сложные state reducers, встроенный streaming,
  множественные checkpoint-бэкенды). Минимальный набор уже покрывает
  реальные сценарии Blue (пайплайн `AiAnalysisRun`, `TutorAgent`-роутинг).
- **Ограничение окружения.** Composer-пакеты с GitHub недоступны в песочнице
  разработки (доступен только реестр Packagist) — не решающий фактор сам по
  себе (реализации LangGraph-подобных PHP-библиотек на Packagist тоже нет
  зрелых), но лишний аргумент за "написать самому, раз всё равно предстоит
  разобраться в деталях".

## Альтернативы, которые рассматривались и отклонены

- **LangGraph как Python-микросервис за HTTP** — отклонено: фрагментация
  стека и сетевой прыжок на каждый узел не оправданы для текущего масштаба;
  прямо противоречит цели понять механику, а не делегировать её библиотеке.
- **Готовая PHP-библиотека workflow-оркестрации общего назначения** (если бы
  таковая была доступна) — рассмотрено бы отдельно при появлении, но не
  найдено зрелой альтернативы уровня LangGraph на момент решения; и даже
  при появлении — обучающая ценность написания своей версии остаётся
  весомым фактором (см. `engineering-principles.md`: "если есть два
  разумных варианта, можно выбрать тот, который даёт больше инженерного
  опыта").

## Последствия

- Положительные: полный контроль и понимание механики, никакой
  межъязыковой границы, использование уже отлаженных примитивов Laravel
  (`Bus::batch()`, Horizon) вместо изобретения своей очереди/воркеров.
- Отрицательные: не получаем "бесплатно" продвинутые возможности зрелых
  движков (сложные reducers состояния, встроенные визуальные инструменты
  отладки, готовые интеграции с провайдерами трейсинга) — если они
  реально понадобятся при росте системы, решение стоит пересмотреть явно,
  а не тихо наращивать самодельный движок до переизобретения LangGraph.
