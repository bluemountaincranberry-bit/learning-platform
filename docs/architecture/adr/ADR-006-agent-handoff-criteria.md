# ADR-006: Когда использовать agent-to-agent handoff (и когда — граф вместо него)

## Статус
Принято.

## Контекст

Handoff (`TutorAgent` передаёт управление специализированному агенту,
реализовано как `HandoffTool`, `agent-framework-roadmap.md` раздел 8) —
мощный, но и самый непредсказуемый механизм в системе: решение "кого
вызвать и зачем" принимает модель, а не детерминированный код. Нужны явные
критерии, когда он оправдан, и явная граница, после которой задачу лучше
решать иначе.

## Решение

Handoff используется, когда **все** условия верны:
- задача большая (не закрывается одним `Tool`-вызовом, см. ADR-002);
- нужен собственный reasoning loop у целевого агента;
- есть несколько шагов, и агент-координатор не должен видеть их детали;
- нужен отдельный, изолированный контекст.

**Максимальная глубина handoff — 2** (`TutorAgent → Agent A → {Agent B,
Agent C, ...}`), с проверкой на этапе выполнения (шаг 5.9,
`agent-framework-roadmap.md`). Пример на границе допустимого — сценарий
"подготовь меня к IELTS за 3 месяца": `TutorAgent → PlanningAgent →
{SpeakingAgent, GrammarAgent, ExerciseAgent}` — ровно глубина 2, дальше не
идёт (см. `ai-platform-vision.md`, раздел 6).

**Правило "graduate to Workflow"**: если конкретная композиция handoff'ов
повторяется регулярно и её структура заранее известна (не придумывается
моделью каждый раз заново) — она переводится из model-directed handoff в
явный `GraphDefinition` с `ParallelNode` (Workflow Engine, ADR-004), а не
остаётся цепочкой `HandoffTool`-вызовов. Handoff остаётся для случаев, где
структура запроса реально не предсказуема заранее.

## Почему

- **Стоимость и предсказуемость.** Каждый handoff — минимум ещё один
  `AgentLoop`, то есть ещё один-несколько LLM-вызовов. Без явной глубины
  цепочка `A → B → C → D` может расти неконтролируемо на реальном трафике.
- **Отладка.** Двухуровневый handoff трассируется как дерево из 2 уровней
  (раздел 10, `ai-platform-vision.md`) — читаемо. Глубже — дерево быстро
  становится нечитаемым, а стоимость и задержка — непредсказуемыми.
- **Graph дешевле там, где структура известна.** Явный `ParallelNode` не
  тратит LLM-вызов на решение "кого вызвать" — решение уже зашито в
  `GraphDefinition`. Model-directed handoff оправдан ровно там, где эта
  гибкость реально нужна (структура запроса заранее не известна) — не как
  дефолт для всего, что выглядит как "несколько агентов работают вместе".
- **Безопасность не должна "размываться" через цепочку.** `sideEffect`
  инструмента handoff не может быть менее строгим, чем самый широкий
  `sideEffect` целевого агента (шаг 5.3/5.9, `agent-framework-roadmap.md`)
  — иначе двухуровневый handoff становится обходом правила "агент не
  публикует без подтверждения человека" через промежуточного агента.

## Альтернативы, которые рассматривались и отклонены

- **Неограниченная глубина handoff** — отклонено: непредсказуемая стоимость
  и риск циклов (`A → B → A → B`), даже при наличии `MAX_ITERATIONS` внутри
  каждого отдельного `AgentLoop`.
- **Всегда граф, никогда model-directed handoff** — отклонено: часть
  запросов пользователя реально непредсказуемы по структуре ("подготовь
  меня к IELTS" может по-разному декомпозироваться в зависимости от
  текущего уровня и целей) — жёстко зашитый граф на всё лишает систему
  гибкости, которая и есть основная ценность LLM-координатора.

## Последствия

- Положительные: чёткий, проверяемый критерий "handoff vs граф" для новых
  фич, встроенная защита от неконтролируемого роста стоимости/глубины.
- Отрицательные: требует периодического ревью — паттерны, которые начинались
  как "непредсказуемый handoff", могут со временем стать регулярными и
  заслуживать перевода в граф; это ручное решение, не автоматическое.
