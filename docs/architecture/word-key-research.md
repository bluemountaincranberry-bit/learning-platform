# VIK-5: word identity and `type:text` inventory

Research date: 2026-10-03. Primary evidence is the checked-in application code and migration history; no production database was inspected. Findings describe the current code, not a verified production data distribution. This note is input to the identity ADR and migration plan, not an implementation change.

## Current identity and state

Canonical vocabulary identity is `lexemes.id`; its natural uniqueness is `(language, normalized_lemma)`. Part of speech and sense are not part of that uniqueness constraint. See [catalog migration](../../src/database/migrations/2026_03_23_180000_create_grammar_catalog_tables.php#L41). `CanonicalLexemeSyncService::syncLemma()` trims and lowercases the lemma and resolves by language plus normalized lemma; `sync()` lowercases the content language and uses occurrence text when a real lemma is unknown. See [sync service](../../src/app/Modules/Content/Application/CanonicalLexemeSyncService.php#L21). Consequently a tokenizer-created `ran` need not resolve to `run`, whereas the known-lemma AI path can pre-resolve it ([service explanation](../../src/app/Modules/Content/Application/CanonicalLexemeSyncService.php#L35)).

`content_lexemes.id` identifies an occurrence/context row with `content_id`, `type`, and displayed `text`; `(content_id, type, text)` has no unique constraint ([original schema](../../src/database/migrations/2026_03_02_100001_create_content_lexemes_table.php#L11)). Its canonical `lexeme_id` is nullable and uses `nullOnDelete` ([canonical FK migration](../../src/database/migrations/2026_07_25_120000_add_lexeme_id_to_content_lexemes_table.php#L12)). Creation auto-syncs only if the canonical ID is missing; editing displayed text does not trigger this hook ([model](../../src/app/Modules/Content/Domain/Models/ContentLexeme.php#L35)). Optional senses are separate, unique per `(lexeme_id, normalized_gloss)` ([sense schema](../../src/database/migrations/2026_08_23_150000_create_lexeme_senses_table.php#L20)).

Context-check state is already canonical: `(user_id, lexeme_id)` is unique and stores only `last_result` and `checked_at`, not a schedule or attempt history ([context-check migration](../../src/database/migrations/2026_08_15_140000_create_user_lexeme_context_checks_table.php#L24)). Self-check reads confidence keyed by occurrence ID ([SelfCheckService:46](../../src/app/Modules/Learning/Application/SelfCheckService.php#L46)) but writes context-check status through canonical ID ([SelfCheckService:167](../../src/app/Modules/Learning/Application/SelfCheckService.php#L167)); the content learner-state adapter reads canonical IDs needing another context review ([ContentLearnerStateReader:33](../../src/app/Modules/Learning/Application/ContentLearnerStateReader.php#L33)). These adapters must keep occurrence context distinct from canonical word state.

## Migration implications inferred from the code

1. **Language collisions are already possible.** SRS uniqueness ignores language and content, unlike canonical identity. Two different languages with the same displayed word reuse a card; `firstOrCreate` keeps the first content context. Backfill can identify that retained context, but cannot recover a second card/history that was never created. Sources: SRS schema and create listener above.
2. **Canonical duplicates can arise during backfill.** Different inflections (`run`/`ran`), case variants, or word/phrase type labels can resolve to one canonical ID while currently owning separate cards. Resolve IDs before enforcing `(user_id, lexeme_id)` uniqueness; reparent every review to a deterministic surviving card before removing duplicates. A winner's schedule/ease and all history need an explicit decision. Sources: canonical sync, SRS schema, cascading review FK above.
3. **Ambiguous occurrence joins can multiply rows.** Since occurrence text is not unique within content, current key joins can return multiple rows/card and `value('id')` has no deterministic ordering. A backfill must classify zero/one/multiple canonical matches, not silently select the first occurrence. Sources: occurrence schema, repository join and reference reader above.
4. **Orphans are supported today.** Due endpoints retain cards with no text match and display the stripped key; nullable review context allows that path. A new required canonical FK needs a quarantine/repair or documented exclusion strategy with before/after counts; it must not hide this as successful migration. Sources: repository fallback, SrsFlowTest orphan scenario above.
5. **Deletion policy matters independently of identity.** Canonical progress is still destroyed with its originating content occurrence, cards/reviews with their content/card, and confidence with its occurrence. Simply adding a canonical column does not preserve user learning when content is removed. Sources: schema table above.
6. **Review context belongs to the answer.** Review submission checks supplied occurrence against the card's stored content, and otherwise infers context from the text key. A canonical card serving several contexts needs validation against canonical identity plus the chosen answer context, while retaining transcript/content evidence. Sources: [SrsController:38](../../src/app/Modules/Srs/Interfaces/Http/Controllers/SrsController.php#L38), [SrsService:64](../../src/app/Modules/Srs/Application/SrsService.php#L64).
7. **Confidence consolidation is separate from progress.** Confidence values are independently updated per occurrence and are bounded scores rather than additive counters. Preserve source rows/audit evidence until a merge policy is agreed; canonical progress needs no second identity conversion. Sources: confidence service and progress migrations above.
8. **Replacing key strings with numeric IDs requires replacing display paths.** Prefix stripping currently supplies user-facing words, mistake events, and AI tool data. New identifiers must not leak into those fields. Sources: backend display/parser inventory above.
9. **A free string does not prove a lexical card.** The schema accepts any `item_key`, and the resolver explicitly accepts colonless strings. No production writer of a distinct nonlexeme key kind was found; test/manual/imported rows nevertheless cannot be assumed lexical from the schema. Migration preflight must classify unsupported key prefixes and unresolvable manual keys, retaining original keys as audit evidence. Sources: SRS schema and reference reader above. This is a compatibility caveat, not a claim that nonlexeme cards exist in production.
