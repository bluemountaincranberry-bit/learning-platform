## Why

Первый rewrite создал модульные пространства имён, но оставил взаимные зависимости Learning/SRS, доступ AI к persistence Content и frontend domains, переэкспортирующие корневую реализацию. Нужен следующий завершённый этап: понятные владельцы поведения, единый предметный словарь и автоматические проверки архитектуры до выхода приложения в production.

## What Changes

- Завершить Laravel-native modular monolith: Eloquent внутри владельца, небольшие Actions/Queries, отдельные классы сложных правил, публичные Contracts/Data.
- **BREAKING**: заменить внутренние namespaces, межмодульные контракты и compatibility aliases; согласованно обновить всех потребителей.
- Разделить AI capabilities, providers, prompts, runtime, retrieval, evaluation и observability. Перенести применение AI-кандидатов к владельцу каталога.
- Определить бизнес-события, момент публикации, идемпотентность реакций и обработку сбоев. Сохранить синхронные транзакции для атомарных изменений.
- Завершить frontend domains/pages, TanStack Query, reusable UI и единый naming, используя s365 как пример организации.
- Добавить исполняемые архитектурные ограничения и доказательства завершения каждого этапа.

## Capabilities

### New Capabilities

Это инженерные и операционные контракты, впервые фиксируемые в пустом OpenSpec: новые проверки зависимостей, правила AI-вызовов, доставки событий и согласованности клиентского состояния. Новые пользовательские функции не заявляются.

- `module-boundaries`: проверяемые границы PHP-модулей и владение изменением состояния.
- `ai-execution`: типизированное выполнение AI-возможностей и наблюдаемость ошибок.
- `business-events`: публикация после commit и безопасная повторная обработка.
- `frontend-domains`: публичные frontend domains и согласованность server state.
- `naming-conventions`: единый словарь и проверки конвенций.

### Modified Capabilities

Нет: существующих OpenSpec specs пока нет.

## Impact

Владельцы: User, Content, Learning, SRS, AI; Admin — адаптеры Filament/SPA; Infrastructure — очереди и технические интеграции. Изменения затрагивают `src/app`, SPA, тесты, CI и архитектурную документацию. Миграции и внешние API меняются только при документированной необходимости; это не разрешение удалять локальные данные.

### Non-goals

Микросервисы, обязательный Kafka для внутренних вызовов, event sourcing, замена UI-библиотеки, новые продуктовые возможности, универсальные repositories для каждой модели и переписывание соседнего s365.

### Decisions requiring approval

Документы описывают предлагаемый implementation scope; их создание не означает запуск реализации. При реализации отдельно фиксируются необходимые изменения внешних API/schema, перенос владения учебными таблицами и граница существующих Filament/SPA admin-сценариев. До этих решений сохраняются пользовательские возможности и данные.
